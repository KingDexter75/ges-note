1. PRESENTATION GENERALE
================================================================================

GesNote2 (« EduNeum ») est une application web multi-roles destinee a la
gestion scolaire : annees/trimestres/sequences, classes, eleves, enseignants,
notes, bulletins, assiduite, vie scolaire et statistiques.

Principes architecturaux :
  - Un backend Django unique (app `eduneum`) expose une API JSON et sert les
    pages HTML/JS/CSS statiques du front.
  - Le front est une application de type SPA sans framework : HTML + JS
    vanilla organises par espace (admin, censeur, enseignant).
  - La persistance se fait via un « instantane » (snapshot) : le front charge
    l'etat complet via GET /api/bootstrap/ et l'enregistre via POST /api/store/
    (avec verification des droits par DIFF cote serveur).
  - L'authentification utilise des JWT HS256 signes (implementation maison
    dans eduneum/jwtauth.py), transportes par cookies HttpOnly, avec rotation
    du refresh token et OTP par SMS optionnel.
  - Roles : admin, direction, censeur, surveillant, enseignant.

Roles et espaces :
  - admin / direction  -> espace `admin/`   (18 pages)
  - censeur            -> espace `censeur/` (9 pages)
  - surveillant        -> menu restreint (tableau de bord, absences, classes)
  - enseignant         -> espace `enseignant/` (6 pages)

Langue : fr-fr par defaut, i18n FR/EN cote front (js/core/i18n.js).
Fuseau horaire : Africa/Douala.

2. PREREQUIS ET INSTALLATION
================================================================================

Prerequis :
  - Python 3.14+
  - MySQL 8 (ou MariaDB 10.6+) sur 127.0.0.1:3306
  - Acces reseau au navigateur (CDN : cdn.tailwindcss.com,
    code.iconify.design)

Etapes :

  2.1 Recuperer le code
      git clone <url-du-depot> GesNote2
      cd GesNote2

  2.2 Creer l'environnement virtuel
      Windows (PowerShell) :
          python -m venv env
          env\Scripts\Activate.ps1
      Linux / macOS :
          python3 -m venv env
          source env/bin/activate

  2.3 Installer les dépendances
      pip install -r requirements.txt

      Contenu de requirements.txt :
          Django==6.1.2
          PyMySQL==1.2.3
          asgiref==3.12.1      (transitive)
          sqlparse==0.6.0      (transitive)
          tzdata==2026.5       (transitive)

  2.4 Creer la base de donnees
      Se connecter a MySQL (compte root par defaut) :
          CREATE DATABASE gesnotes2
            CHARACTER SET utf8mb4
            COLLATE utf8mb4_unicode_ci;

  2.5 Appliquer les migrations
      python manage.py migrate

  2.6 Creer le compte administrateur
      python manage.py admin_init
      Compte par defaut : telephone 672647904 / mot de passe admin1234
      Options : --telephone 6XXXXXXXX --mot-de-passe MonMotDePasse

  2.7 Demarrer le serveur
      python manage.py runserver
      Ouvrir http://127.0.0.1:8000/

Remarque : le projet demarre vide ; aucune donnee de demonstration n'est
inseree. Le dossier `env/` (venv) ne doit pas etre versionne.

5. BASE DE DONNEES ET MODELES
================================================================================

Base MySQL `gesnotes2`, pilote PyMySQL (active par
pymysql.install_as_MySQLdb() dans config/__init__.py).

Principes de modelisation (eduneum/models.py) :
  - Chaque modele correspond a une collection du localStorage d'origine
    (js/core/store.js).
  - PK = chaines produites par le front (`e1`, `c1`, `an2025`...), sauf
    Compte, Coefficient, Parametres.
  - Dates/horodatages souvent stockes en texte ISO (CharField) pour rester
    fideles au front, y compris chaines vides.
  - db_table explicite pour chaque modele (prefixe `eduneum_`).
  - Migrations : 0001_initial -> 0008_eleve_redoublant.

6. AUTHENTIFICATION (JWT + OTP)
================================================================================

Implementation : eduneum/jwtauth.py (JWT HS256 maison, sans PyJWT),
eduneum/views.py (flux), eduneum/middleware.py (lecture des jetons).

--------------------------------------------------------------------------------
6.1 JETONS
--------------------------------------------------------------------------------

Access token :
  - Portee : telephone (sub), role, enseignant_id (ens), typ, iat, exp
  - TTL : 12 h (JWT_ACCESS_TTL_SECONDS = 43200)
  - Cookie HttpOnly `eduneum_access`, path /, SameSite=Lax
  - Egalement lisible en header Authorization: Bearer

Refresh token :
  - TTL : 7 j (JWT_REFRESH_TTL_SECONDS = 604800)
  - `jti` = secrets.token_hex(16), trace en base (modele RefreshToken)
  - Cookie HttpOnly `eduneum_refresh`, path /api/auth/, SameSite=Lax
  - Rotation a chaque usage : l'ancien jti est rejete, un nouveau est cree

Secret : settings.JWT_SECRET si defini, sinon SECRET_KEY.

--------------------------------------------------------------------------------
6.2 FLUX DE CONNEXION
--------------------------------------------------------------------------------

Etape 1 - POST /api/auth/otp/
  - Verifie telephone + mot de passe (check_password, is_active) -> 401 si KO.
  - Si OTP non obligatoire (OTP_OBLIGATOIRE=None et SMS non configure) ->
    connexion immediate : emet la paire de jetons.
  - Sinon genere un code OTP a 6 chiffres (validite 300 s, tentatives max 5),
    l'envoie par SMS (eduneum/sms.py), supprime les codes non utilises.
  - Reponse : {ok, telephone, ttl}.

Etape 2 - POST /api/auth/verify/
  - Verifie le code : existence, expiration, tentatives < 5 (sinon 429),
    egalite (sinon incrementation de tentatives, 401).
  - Marque le code utilise, emet la paire de jetons, pose les cookies.
  - Reponse : {ok, direct, session, destination, accessToken, refreshToken}.

Renouvellement - POST /api/auth/refresh/
  - Verifie le refresh (signature, typ, exp, ligne RefreshToken non expiree,
    compte actif).
  - Rotation : supprime l'ancien jti, emet une nouvelle paire, re-pose les
    cookies.

Deconnexion - POST /api/auth/logout/
  - Revoque le refresh token courant (suppression du jti en base),
    efface les cookies.

Changement de mot de passe - POST /api/mot-de-passe/
  - Verifie l'ancien mot de passe, nouveau >= 6 caracteres et different.
  - Revoque TOUS les refresh tokens du compte.

--------------------------------------------------------------------------------
6.3 MIDDLEWARE
--------------------------------------------------------------------------------

eduneum/middleware.py : JWTAuthenticationMiddleware
  - A chaque requete, lit le jeton (cookie ou Bearer).
  - Si charge valide et compte actif -> request.user = compte.
  - Sinon request.user reste l'AnonymousUser.
  - Aucune session Django utilisee pour l'authentification.

================================================================================
7. API REST
================================================================================

Routes definies dans eduneum/urls.py ; vues dans eduneum/views.py.
Le routing est monte a la racine par config/urls.py
(/django-admin/ + inclusion eduneum.urls).

--------------------------------------------------------------------------------
7.1 AUTHENTIFICATION
--------------------------------------------------------------------------------

POST /api/auth/otp/
  Etape 1 de connexion : telephone + mot de passe.
  Genere et envoie le code OTP si la passerelle est activee, sinon connecte.
  Reponse : {ok, telephone, ttl}

POST /api/auth/resend/
  Meme vue que otp/ : renvoie un nouveau code OTP.

POST /api/auth/verify/
  Etape 2 : verification du code a 6 chiffres -> emission des jetons.
  Reponse : {ok, direct, session, destination, accessToken, refreshToken}

POST /api/auth/refresh/
  Rotation du refresh token, nouvelle paire de jetons.

POST /api/auth/logout/
  Revoque le refresh token et efface les cookies.

--------------------------------------------------------------------------------
7.2 DONNEES (INSTANTANE)
--------------------------------------------------------------------------------

GET /api/bootstrap/            (require_GET, never_cache)
  Charge la session + l'instantane complet de la base.
  Reponse : {ok, session, db: snapshot()}
  401 si non connecte.

POST /api/store/               (csrf_exempt)
  Reoit l'instantane complet du front.
  verifie les droits via droits.verifier_ecriture_instantane() puis
  snapshot.restore(data) (diff incrémental ou restauration complete).
  Reponse : {ok, version: 4}
  Erreurs : 401 / 400 / 403 / 500

POST /api/reset/
  Remet a zero les donnees metier (snapshot.wipe_business()).
  Reserve aux roles admin et direction.
  Conserve les comptes et les parametres.

--------------------------------------------------------------------------------
7.3 COMPTES ET PROFIL
--------------------------------------------------------------------------------

GET /api/comptes/
  Liste des comptes (admin/direction uniquement).

POST /api/comptes/             (csrf_exempt)
  Cree / met a jour / desactive (actif:false) un compte.
  Reserve aux roles admin et direction.

POST /api/mot-de-passe/
  Changement du propre mot de passe de l'utilisateur connecte.
  Revoque tous ses refresh tokens.

--------------------------------------------------------------------------------
7.4 ROUTING DES PAGES (CATCH-ALL)
--------------------------------------------------------------------------------

GET ^(?P<path>.*)$  ->  views.serve_page(request, path)

  - Normalise le chemin (vide ou fin / -> index.html).
  - Protege contre le path-traversal (le chemin resolu doit rester sous
    la racine du projet).
  - Fichiers non-HTML : servis via _serve_asset() avec table TYPES_MIME
    explicite (js, css, html, svg, png...).
  - index.html : si connecte -> redirect vers l'accueil du role ;
    sinon session null injectee.
  - Pages HTML :
      non connecte   -> redirect /index.html?suite=<path>
      role non autorise -> redirect vers l'accueil du role
      sinon -> injection dans <head> de :
        window.__EDUNEUM_SERVER__ = true
        window.__EDUNEUM_SESSION__ = {...}
  - @ensure_csrf_cookie sur chaque page.

Constantes utiles dans views.py :
  PAGE_MODULES  page HTML -> module de droits
  LIRE          module -> roles autorises en lecture
  ROLES_GESTION_COMPTES = {'admin', 'direction'}
  ROLES_COMPTE  = les 5 roles
  accueil_pour(role) : enseignant -> enseignant/tableau-de-bord.html,
                       sinon admin/tableau-de-bord.html

================================================================================
8. DROITS ET PERMISSIONS
================================================================================

Fichier : eduneum/droits.py (miroir serveur de js/core/acces.js).
Principe : controle par DIFF - le front soumet l'instantane complet, le
serveur le compare a l'etat reel de la base et n'autorise que les
changements permis au role de l'utilisateur.

Collections techniques exemptees de condition de role :
  - journal     : append-only (ajout uniquement, sauf cas ci-dessous)
  - sequenceur  : compteur d'identifiants, ne peut que croitre

--------------------------------------------------------------------------------
8.1 MATRICE D'ECRITURE PAR MODULE (MODULES_ECRITURE)
--------------------------------------------------------------------------------

admin_only :
  admin_notes                          -> admin

admin + direction :
  admin_annees, admin_classes, admin_matieres, admin_eleves,
  admin_personnel, admin_inscriptions, admin_migrations,
  admin_affectations, admin_bulletins, admin_statistiques,
  admin_rapports, admin_vie_scolaire, admin_journal, admin_parametres

+ surveillant :
  admin_assiduite                      -> admin, direction, surveillant

Censeur :
  censeur_assiduite                    -> censeur, admin, direction,
                                         surveillant
  censeur_vie_scolaire                 -> censeur, admin, direction

Enseignant :
  teacher_saisie                       -> enseignant, admin
    (la direction n'ecrit PAS les notes)
  teacher_ma_classe                    -> enseignant seul
    (espace professeur principal)

Refus par defaut : un module non liste est interdit.

--------------------------------------------------------------------------------
8.2 COLLECTIONS HABILITEES (COLLECTIONS)
--------------------------------------------------------------------------------

Chaque collection d'instantane est liee a un ou plusieurs modules :
  notes            <- teacher_saisie, admin_notes
  appreciations    <- admin_bulletins, teacher_ma_classe
  sequences        <- admin_annees
  smsLog           <- admin_parametres
  parametres       <- admin_parametres
  sequenceur       <- admin_parametres
  journal          <- admin_journal
  (refus par defaut si la collection n'est pas listee)

--------------------------------------------------------------------------------
8.3 VERIFICATIONS SPECIFIQUES
--------------------------------------------------------------------------------

Annees cloturees :
  Une annee avec cloturee=True est en lecture seule pour tous, sauf
  reactivation explicite par admin/direction (_annees_reactivées).

Notes :
  - Sequence verrouillee -> ecriture refusee.
  - Trimestre ferme -> ecriture refusee.

Portee enseignant :
  - Un enseignant n'ecrit des notes que dans SES affectations
    (classe x matiere non archivees).
  - Appreciations : reservees au prof principal de la classe.

Journal d'audit :
  - Append-only.
  - Suppression uniquement en prefixe : au plus 150 lignes si >= 450
    existantes (garde-fou anti-croissance).

Sequenceur :
  - Le compteur d'identifiants ne peut qu'augmenter.

--------------------------------------------------------------------------------
8.4 FONCTION PRINCIPALE
--------------------------------------------------------------------------------

droits.verifier_ecriture_instantane(compte, data)
  -> None si accepte
  -> {ok: False, motif: "..."} si refuse

Etapes : 1) role valide + matrice des modules
         2) journal / sequenceur
         3) annees cloturees
         4) sequences / trimestres
         5) portee enseignant

Fonctions helpers :
  _canon(v)             forme canonique (12 == 12.0, None == '')
  _ligne_identique      comparaison d'une ligne
  _diffs(data, courant) -> {collection: {ajoutes, modifies, supprimes}}
  _affectations_enseignant(id) -> set (classeId, matiereId)
  _est_prof_principal(...)
  _annee_de_classe / _annee_de_sequence / _annee_cloturee
  _sequence_bloquee / _trimestre_ferme

9. INSTANTANE (SNAPSHOT)
================================================================================

Fichier : eduneum/snapshot.py (~833 lignes).
Role : conversion base de donnees <-> instantane JSON (forme identique au
localStorage d'origine utilisee par le front).

--------------------------------------------------------------------------------
9.1 CHARGEMENT - snapshot() (DB -> JSON)
--------------------------------------------------------------------------------

Construit un dictionnaire avec les collections suivantes :
  annees (avec trimestres imbriques), sequences, sections, classes,
  matieres, enseignants, eleves, inscriptions, affectations,
  profsPrincipaux, affectationsCenseurs, coefficients, notes, absences,
  sanctions, disciplines, migrations, decisions, appreciations,
  bulletinsValides, journal, smsLog, parametres, sequenceur

Details :
  - _parametres_complets / _sequenceur_complet : fusion avec
    PARAMETRES_DEFAUT / SEQUENCEUR_DEFAUT (eduneum/seed.py) pour ne
    jamais priver le front.
  - SECTIONS_DEFAUT : sec-fr (Francophone), sec-en (Anglophone).

--------------------------------------------------------------------------------
9.2 RESTAURATION - restore(data)
--------------------------------------------------------------------------------

Marquee @transaction.atomic.

Cas 1 - Instantane vide (data sans donnees) :
  _restore_complet(data) : reconstruction totale.
  _wipe() d'abord : suppression dans l'ordre inverse des dependances
  (24 tables).

Cas 2 - Instantane non vide :
  Restauration incrémentale :
    _cibles()                description de chaque collection
                             (cle JSON, modele, pk, champs)
    _normaliser(data)        trimestres aplatis depuis les annees
    _etat_collection         1 lecture DB par collection
    _supprimer               enfants -> parents
    _inserer_mettre_a_jour   bulk_create / bulk_update par lots de 500
    _synchroniser_coefficients remplacement en bloc (pas de PK propre)
  Ecriture finale de Parametres (parametres + sequenceur).

--------------------------------------------------------------------------------
9.3 REINITIALISATION - wipe_business()
--------------------------------------------------------------------------------

Supprime toutes les donnees metier (23 tables) en conservant :
  - Parametres
  - Les comptes (utilisateurs)
Utilisee par POST /api/reset/ (bouton « Réinitialiser » de l'interface).
Etat vide final ; aucune donnee de demo rechargee.

11. PASSERELLE SMS
================================================================================

Fichier : eduneum/sms.py (Africa's Talking, urllib uniquement).

Variables d'environnement (jamais de secret dans le depot) :
  AT_USERNAME   nom d'utilisateur Africa's Talking (obligatoire si SMS)
  AT_API_KEY    cle API (obligatoire si SMS)
  AT_SENDER_ID  expediteur alphanumerique (facultatif)
  AT_SANDBOX    "0" pour la production (defaut : "1" bac a sable)
  SMS_PAYS      indicatif pays par defaut ("+237" Cameroun)

Comportement :
  - Envoi des codes OTP uniquement (eduneum/views.py, _creer_otp).
  - Si la passerelle n'est pas configuree (AT_USERNAME/AT_API_KEY vides),
    l'OTP est desactive : connexion directe telephone + mot de passe
    (OTP_OBLIGATOIRE = None).
  - Si l'envoi echoue, le code est trace dans les logs serveur et
    JAMAIS renvoye au navigateur.
  - Chaque envoi est journalise (modele SmsLog).

Reglage OTP_OBLIGATOIRE (config/settings.py) :
  None   automatique - OTP requis si la passerelle est configuree
  True   OTP toujours exige (meme sans passerelle : echec de connexion)
  False  jamais d'OTP (connexion directe)

13. MISE EN PRODUCTION
================================================================================

Avant toute mise en production, imperativement :

  1. Changer SECRET_KEY dans config/settings.py
     (generer une cle aleatoire : python -c
      "from django.core.management.utils import \
get_random_secret_key; print(get_random_secret_key())")

  2. Passer DEBUG = False

  3. Restreindre ALLOWED_HOSTS aux domaines reels
     (supprimer ['*'])

  4. Securiser la base de donnees : mot de passe MySQL fort, user dedie
     (pas root), modifier DATABASES dans settings.py

  5. Configurer les variables d'environnement SMS pour la production :
     AT_SANDBOX=0, AT_USERNAME et AT_API_KEY valides

  6. Servir via un serveur WSGI/ASGI de production
     (gunicorn/uwsgi/uvicorn ou waitress sous Windows) avec config.wsgi
     ou config.asgi ; derriere un reverse proxy (nginx/Apache) avec HTTPS

  7. Generer les fichiers statiques si necessaire :
     python manage.py collectstatic
     (le projet sert principalement les fichiers via la vue catch-all)

  8. Exclure du depot : env/, __pycache__/, *.pyc

  9. Sauvegarder regulierement la base MySQL (mysqldump)
